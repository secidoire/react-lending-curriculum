# カリキュラム詳細
全12回（第0部4回、第1部8回）＋発展編2回、1回60〜90分。各回の流れ：前回の仕様変更チェック → 困りごと体験 → ハンズオン（ジュニアが先に書く）→ 問いによるレビュー → 次回予告。
各回の説明は `explainer/src/sessions/<回>.mdx` に書く。ページの節の順番は `docs/explainer-spec.md` の「各回のページ構成」に従う。

## 第0部：基礎編

### 0-1 ブラウザとDOM
- **ゴール**：HTMLファイルとDOMが別物だと説明できる。DOMを変更すると再計算が走ると知る。
- **困りごと**：「ソース表示」とElementsパネルの内容が違う。
- **概念**：パース → DOM/CSSOM → スタイル計算 → レイアウト → ペイント → コンポジット（MDN・web.dev準拠）。 
- **ハンズオン**：(1) ソース表示とElementsを見比べる (2) Elementsで書き換えてからリロードし、元に戻ることを確かめる (3) Consoleで `textContent` を変更する (4) Paint flashingで「色を変える」と「幅を変える」を比べる (5) 1000行を1行ずつappendした場合とFragmentでまとめた場合を比べる。
- **模範解答の要点**：HTMLはDOMの初期値にすぎない。
- **レビューの問い**：「innerHTMLで毎回全部作り直すと、何が失われる？」（フォーカス・入力値。0-3への伏線）
- **よくある誤解**：「DOM操作は常に遅い」。実際に重いのはレイアウトの再計算や、読み書きを交互に繰り返すこと。 
- **次回予告**：素のJSで一覧に追加・削除・フィルタを付ける。

### 0-2 素のJSで貸出一覧（命令的UIの限界）
- **ゴール**：データとDOMを二重管理すると同期漏れが起きることを、体験して言葉にできる。
- **困りごと**：機能を足すたびに件数表示の更新漏れや、フィルタ中に追加した行が表示されるといったバグが出る。
- **ハンズオン**：(1) createElementで一覧を作る (2) 追加 (3) 削除 (4) 「貸出中のみ」フィルタ (5) 仕様追加「貸出中N件」の表示（更新箇所が散らばるのを体験する）。
- **模範解答の要点**：2つの版を用意する。(A) 差分を手で書く版は同期バグが起きやすい。(B) `render()`で全部作り直す版は単純だがフォーカスが消える。
- **レビューの問い**：「延滞表示を足すと何か所直す？」
- **よくある誤解**：「DOM APIが悪い」。問題は、状態が2か所にあること。
- **次回予告**：(B)の単純さのまま、フォーカスを消さない方法を作る。

### 0-3 ミニReactを自作（山場）
- **ゴール**：UI = f(state) を自分で実装し、仮想ノードが「全部描き直す単純さ」と「最小限のDOM変更」を両立させる手段だと理解する。keyとJSXの正体を説明できる。
- **困りごと**：全部描き直す方式だと、入力中にフォーカスが消える。
- **ハンズオン（steps/01〜07）**：(1) `h(type, props, ...children)` がオブジェクトを返す (2) `createDom` (3) setStateで全部描き直す (4) フォーカスが消えるのを体験する（デモa） (5) 前回の仮想ノードと比べる `patch` を書く（typeが同じなら属性とテキストを更新、違えば置換、子は先頭から順に比較） (6) 先頭に追加すると入力値がずれるのを体験し、keyで対応付ける（Mapを引く最小実装でよい） (7) `/** @jsx h */` を付けて、JSXが h() の呼び出しになることを確かめる。
- **模範解答の要点**：約200行の `mini-react.js` と、Reactとの対応表（h↔createElement、patch↔reconciliation、DOM反映↔commit）。Fiber・Hooksはやらない。
- **レビューの問い**：「この差分更新は、常に直接DOMに書くより速い？」→ 速くない。差分計算そのものが追加のコストになる（Svelteの記事）。それでも使うのは、状態遷移を考えずに書けるから。
- **よくある誤解**：「仮想DOMだから速い」「再レンダリングはDOMの全書き換え」「keyは警告を消すため」「JSXはHTML」。
- **次回予告**：Hooksでつまずく3つのJSの性質を学ぶ。

### 0-4 Hooksの前提になるJS
- **ゴール**：クロージャ・参照の等価性・イミュータブル更新の3つで、Hooksの代表的なバグを説明できる。
- **困りごと（先に見せる）**：(1) `push`してからsetStateしても画面が変わらない (2) `setInterval(() => setCount(count + 1))`（依存配列は`[]`）が1で止まる (3) 依存配列に`{ q }`を入れると毎回実行される。
- **ハンズオン**：(1) `makeCounter`を作り、ループでの`var`と`let`の違いを見る (2) `Object.is`クイズ (3) ネストした貸出データをイミュータブルに更新する関数3つ（テスト付き） (4) ミニReactに`useState`もどきを足し、レンダーごとのスナップショットを確かめる (5) デモcを見ながら、(2)の3通りの直し方（関数型更新・依存配列・useEffectEvent）を議論する。
- **模範解答の要点**：(1) 参照が同じなので変化なしと判定される (2) 初回の count を捕まえ続けている (3) 毎回新しいオブジェクトが作られる。
- **よくある誤解**：「依存配列は実行タイミングを指定するもの」。正しくは、エフェクトが読むリアクティブな値の宣言。
- **次回予告**：Reactで備品一覧を作る。

## 発展編：Reactの動作原理（第8回の後、全2回）

前提：0-3のミニReact、0-4のJS、第1部をひととおり終えていること。
発展編のゴールは、第1部で「そういうルールだから」と覚えたことを、仕組みから導けるようにすること。
扱う対象はモデルであって、Reactの実装そのものではない。そのことを冒頭で宣言する。

### 発展A-1 stateはどこにあり、Reactはいつ動くのか
- **ゴール**：stateがコンポーネント関数の外（Fiber）に保存されていること、Hooksが呼び出し順で識別されていることを説明できる。setStateは更新の予約であり、Object.isで省略されうることを説明できる。
- **困りごと（冒頭で問う）**：第1部で踏んだ次の3つのバグを並べ、「ルールではなく仕組みで説明できる？」と問う。
  (1) Hooksをif文の中で呼ぶとlintに怒られる (2) `setCount(count + 1)` を3回呼んでも+1にしかならない (3) `push`してからsetStateしても画面が変わらない
- **概念**：関数のローカル変数はreturnで消える → stateは外にある。Hookは位置（呼び出し順）で識別される。トリガーの3種類（自身のsetState・親の再レンダリング・Contextの変化）。更新キューとバッチング。Object.isによる省略。
- **ハンズオン**：steps/01〜05（`docs/advanced-handson-spec.md`）
- **模範解答の要点**：(1) 順番がずれると別のHookの値を読む (2) 3回とも同じスナップショットのcountを使っている (3) 参照が同じなので「変化なし」と判定される。3つとも、0-4のクロージャと参照の等価性の話に帰着する。
- **レビューの問い**：「Hookを名前で識別する設計だったら、ルールはどう変わる？ 代わりに何が不便になる？」
- **よくある誤解**：「Reactは変数を監視している」「setStateを呼ぶと即座に関数が再実行される」「バッチングは最適化のおまけ」（実際は一貫した状態で1回描くための仕組み）
- **次回予告**：比較の結果をDOMに反映するのはいつか。useEffectはいつ動くのか。

### 発展A-2 何を比べ、いつDOMを書き換えるのか
- **ゴール**：レンダーとコミットを区別し、それぞれで何が起きるかを説明できる。参照比較を選んだ理由を、計算量とイミュータブル更新・構造共有の観点から説明できる。
- **困りごと（冒頭で問う）**：(1) 再レンダリングされたのにDOMが変わらないことがあるのはなぜ？ (2) memoしたのに子が再レンダリングされるのはなぜ？ (3) useEffectの中で要素のサイズを測るとちらつくのはなぜ？
- **概念**：レンダーフェーズ（関数を呼び、型・key・propsを前回と比較する。中断・やり直しがありうるので純粋でなければならない）。2本の木（current と workInProgress）。コミットフェーズ（同期・中断なしで差分をDOMに反映）。useLayoutEffect → 描画 → useEffect の順番。依存配列のObject.is比較。参照比較とイミュータブル更新の取引。構造共有。他フレームワーク（Vue・Solid・Svelte 5）のリアクティビティとの対比。React Compilerの位置づけ。
- **ハンズオン**：steps/06〜08（`docs/advanced-handson-spec.md`）とデモ(d)。時間が余れば、解説ページ自体の `explainer/src/router/useHashRoute.ts` を読み、「Reactの外の状態（URL）をどう購読し、いつ再レンダリングを起こしているか」を今日の言葉で説明させる。
- **模範解答の要点**：再レンダリング（関数の再実行）とコミット（DOMの変更）は別物。memoが効かないのは毎回新しい参照のpropsを渡しているから。正規化と構造共有を組み合わせると、変更していない部分の参照が保たれ、スキップされる。データ設計がそのまま再レンダリングの範囲を決める。
- **レビューの問い**：「第4回の正規化は、再レンダリングの範囲にどう効いていた？」「直接代入で動くVueのモデルと比べて、Reactのモデルの得と損は？」
- **よくある誤解**：「再レンダリング＝DOMの書き換え」「深い比較をしてくれればイミュータブルにしなくていいのに」（計算量の話で返す）「useLayoutEffectのほうが早いから常にそっちがいい」
- **まとめ**：Reactの設計は「比較を安くする代わりに、更新の書き方に規律を課す」取引である。この一文を「今日の一文」の候補にする。
