# 解説文と説明図の書き方

読者はジュニアです。JS/TSの文法は書けますが、DOMとReactの内部は曖昧です。
この教材は「困りごとを体験してから原理を知る」順で学ぶので、ふつうの説明文の型（結論を先に書く）をそのまま使うと、学びの核である「自分で気づく」を奪います。このスキルは、その違いを踏まえて解説と図を作るための手順です。

CLAUDE.md の設計原則と用語のルールが常に優先です。ここに書くのは、その原則を文章と図に落とすやり方です。

## 手順

### 1. 書く前に、各まとまりの役割を1行ずつ決める

スライドなら1枚ごと、読み物なら節ごとに、次の2つを1行で書き出してから本文に入ります。

- **問い**：読者がここで抱えているはずの疑問（例：「なぜ入力中にフォーカスが消える？」）
- **持ち帰り**：読み終えた読者が自分の言葉で言えるようになること

先に決める理由は、書きながら決めると1枚に2つの話が入り、どちらも残らないからです。
書き出した「問い」だけを順に読んで、1本の流れになっているかを確かめます。飛躍があれば、そこに読者がつまずく段差があります。

この一覧は、本文を書く前にユーザーに見せます。構成の直しは、本文を書いたあとより安く済みます。

見出しとスライドのタイトルには、原則として**問い**を書きます。答えを書いてよいのは、その答えに読者がたどり着いたあとのまとまり（原理・よくある誤解・今日の一文）だけです。

### 2. 説明は「現象 → 仮説 → 最小の再現 → 原理 → 公式ドキュメント → 用語」の順に並べる

`docs/instructor-guide.md` の「説明の順番」と同じです。用語を最後に出すのは、先に名前を出すと、読者が問題ではなく道具を探し始めるからです。

- **現象**：前回のコードで実際に起きる困りごとを、読者が手元で再現できる形で書く。
- **仮説**：読者に予想させる問いを置く。答えは続けて書かない。
- **最小の再現**：原因だけが残る最小のコード。関係ない行は削る。
- **原理**：ここで初めて仕組みを説明する。1つの段落で1つのことだけを言う。
- **公式ドキュメント**：`docs/references.md` にあるページへリンクする。挙動に自信がなければ、書く前にそのページを確認する。
- **用語**：最後に名前を与える（「いま見たものを reconciliation と呼びます」）。

具体例は、題材の貸出管理アプリから取ります。`foo` や `Counter` のような借り物の例は、読者が自分のコードに結びつける手間を増やします。ただし、原因を1つに絞るための最小の再現では、アプリから離れてもかまいません。

### 3. 図が要るかを判断し、要るなら作る

文章で3文以上かけて位置関係・順序・変化を説明しているなら、図の出番です。逆に、1文で言えることを図にすると、読者は図を読み解く手間だけを払います。

図を作るときは `references/diagrams.md` を読みます。形の選び方、SVGの書き方、実コードとの照合の手順があります。

### 4. 答えの漏れを確かめる

書いた場所ごとに、置いてよい内容が違います。

| 場所 | 答えを書いてよいか |
|---|---|
| お題README（`handson/**/README.md`） | 書かない。ヒントは Hint1→3 の段階にし、答えに近いものほど `<details>` で折りたたむ |
| スライドの「困りごと」「問い」「お題」 | 書かない。お題は1枚で止める |
| スライドの「原理」以降、読み物、講師ガイド | 書いてよい |
| 図 | 置かれる場所のルールに従う。お題に置く図に、模範解答の構造を描かない |

漏れやすいのは、見出し・図のラベル・コード例のファイル名や関数名です（例：お題の図に `patch()` と書いてしまう）。本文だけでなく、そこも見ます。

### 5. 初見の読者に読ませる

書き手は答えを知っているので、説明の穴が見えません。文脈を持たないサブエージェントに、書いた文章**だけ**を渡して読ませます。リポジトリの他のファイルや、こちらの意図は渡しません。

サブエージェントには「JS/TSは書けるが、DOMとReactの内部は曖昧なジュニア」として読んでもらい、次を答えさせます。

1. 何をすればよいか、何が分かればよいかを、自分の言葉で言えるか。
2. 説明なしに出てきた言葉、意味が取れなかった文はどれか。
3. （お題の場合）答えや、答えを強く示すヒントが読み取れてしまう箇所はあるか。
4. （読み物・スライドの場合）読み終えて「今日の一文」を書くとしたら何と書くか。

4の答えが、手順1で決めた「持ち帰り」とずれていたら、説明が届いていません。文章のほうを直します。
サブエージェントを使えない環境では、この4問を自分で順に確かめ、その旨を報告に書きます。

### 6. 意味を変えずに読みやすくする

最後に文章を整えます。日本語の推敲スキル（`japanese-doc-editing` など）が使えるなら、それを使います。

整えるときに変えてはいけないのは、主張・条件・言い切りの強さです。教材では特に次が崩れやすいので、整えたあとに見直します。

- **言い切りを弱めない**：「再レンダリングしてもDOMが変更されるとは限らない」を「変更されないこともあります」にすると、区別の要点がぼやける。
- **条件を落とさない**：「依存配列が `[]` のとき」のような前提を、読みやすさのために削らない。
- **問いを答えに書き換えない**：「どこを直す？」を「ここを直します」にしない。レビューは問いで行う。
- **用語をそろえる**：1つのものを1つの名前で呼ぶ。「再レンダリング」（コンポーネント関数の再実行）と「DOM更新（commit）」を混ぜない。

## 書かないこと

CLAUDE.md の「用語の正確さ」「やってはいけないこと」がそのまま当てはまります。解説文で踏みやすいものだけ挙げます。

- 「仮想DOMがあるから速い」。価値は宣言的UI（UI = f(state)）で、仮想DOMはその手段。
- 「useEffectはライフサイクルメソッドの代わり」。エフェクトは外部システムとの同期。
- 第7回より前に、useMemo / useCallback を最適化の基本として紹介する。
- 困りごとを体験させる前に、Context・カスタムHook・Repository・useReducer の名前を出す。

## 報告に含めること

作業を渡すときに、次を短く添えます。ユーザーが検証の中身を確かめられるようにするためです。

- 手順1の一覧（問いと持ち帰り）
- 初見読者テストで出た指摘と、それぞれをどう直したか（直さなかったものは理由）
- 図を作った場合は、実コード・仕様との照合結果（`references/diagrams.md` の手順4）
