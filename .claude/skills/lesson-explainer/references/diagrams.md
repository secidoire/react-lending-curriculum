# 説明図の作り方

図は「視覚デモ」とは別物です。デモは `docs/demo-spec.md` の3本だけで、操作して現象を体験させるものです。ここで扱う図は、動かない1枚の絵で、順序・変化・構造を一目で見せるものです。動きで見せたくなったら、それは図ではなくデモの領分なので、既存の3本で足りないかを先に考えます。

## 1. 図で言うことを1文にする

1つの図は1つのことだけを言います。その1文をキャプションにします。
1文にできないなら、図を2枚に分けるか、まだ言いたいことが決まっていません。

例：「typeが同じなら、DOMノードは作り直さず属性だけを書き換える」

## 2. 形の候補を2〜3個出して選ぶ

最初に思いついた形で描き始めると、内容に合わない形のまま細部を詰めてしまいます。先に候補を並べ、手順1の1文がいちばん素直に読み取れるものを選びます。選んだ理由を1行で残します。

| 言いたいこと | 向いている形 | この教材での例 |
|---|---|---|
| 順番に起きること | 左から右への流れ図 | パース → DOM → レイアウト → ペイント、render → commit |
| 状態と、その間の移り方 | 状態遷移図 | reserved → lent → returned |
| 前と後で何が変わったか | 左右に並べた比較 | 全部描き直し vs 差分更新、key=index vs key=id |
| 時間とともに値がどう見えるか | 横に並べたスナップショット | レンダー#1 count=0、#2 count=1 とクロージャの参照先 |
| 入れ子・所有の関係 | 木、入れ子の箱 | コンポーネントツリーとpropsの流れ、featureごとのディレクトリ |
| どこに何を置くか | 層の図 | UI / スキーマ / ドメイン / Repository |

表で足りるもの（項目の対応、APIの比較）は表にします。

## 3. 描く

置き場所で形式を決めます。どちらも `file://` で開いて表示でき、外部に何も取りに行かないことが条件です。

- **スライド**：`<section>` の中にインラインの `<svg>` を書く。
- **読み物（Markdown）**：`.svg` ファイルにして `![キャプション](パス)` で参照する。置き場所が決まっていなければ、作る前にユーザーに確認する。

SVGの決まり：

- `viewBox` を指定し、幅は親に合わせる。スライドは 1280×720 の中に収まる大きさにする。
- 文字は `font-family: "Hiragino Sans", "Noto Sans JP", sans-serif`。スライドでは18px以上。後ろの席から読めない文字は、無いのと同じです。
- 外部のフォント・画像・スタイルシートを読み込まない（`@import`、`http` で始まる `href` を書かない）。
- 色は、地の色・文字の色・強調1色を基本にする。強調色は、手順1の1文に関わる部分にだけ使う。
- 色だけで区別しない。線の種類やラベルでも区別できるようにする（投影やモノクロ印刷で色は消える）。
- `role="img"` と `<title>` を付け、図が言っていることを1文で書く。
- ラベルは日本語、識別子は英語のまま書く（`patch`、`dueDate`）。
- 矢印には、何が流れるか・何が起きるかを書く。ラベルのない矢印は、読者が意味を推測することになる。
- アニメーションは付けない。段階を追って見せたい場合だけ、reveal.js の `class="fragment"` で順に表示する。

1枚に入れる要素は、7個前後までを目安にします。それより多いなら、言いたいことが2つ以上あります。

## 4. 実コードと仕様に照合する

図は文章より信用されます。図の中の名前が実際のコードと1文字違うだけで、読者は検索して見つからず、そこで止まります。描き終えたら、図に書いたものを1つずつ確かめます。

1. 図の中の識別子（関数名・型名・状態名・フィールド名・ファイル名）をすべて書き出す。
2. それぞれを、その回の `solution/` と `docs/domain-spec.md` で検索する。見つからないものは、図を直すか、まだ存在しないことを図に明記する。
3. 矢印（遷移・呼び出し・データの流れ）が、コードや仕様で実際に起きるものかを確かめる。
4. Reactやブラウザの挙動を描いた図は、`docs/references.md` にある公式ページの説明と食い違っていないかを確かめる。

この教材で特に間違えやすい点：

- **延滞は状態ではない**。状態遷移図に「延滞」の箱を描かない。`isOverdue(loan, now)` で導出する値として、図の外に注記する。
- **cancel は第7回で追加される**。第4〜6回の状態遷移図には描かない。
- **再レンダリングとcommitは別の段階**。1つの箱にまとめない。
- **仮想ノードの比較を「速くする仕組み」として描かない**。描くのは「全部描き直す単純さのまま、DOMの変更を最小にする」こと。

照合の結果は、報告に「確かめた識別子の一覧と、参照したファイル」として添えます。
