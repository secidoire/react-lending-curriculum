## Reactのコードを、少しだけ読めるようにするには？

今日の例には、本物のReactのコードが出てきます。書き方は次回から扱うので、ここでは前回のミニReactとの対応だけを押さえます。

<Sandbox spec={counterSandbox} />

| 前回のミニReact | Reactでの書き方 | 役割 |
|---|---|---|
| `view()` | `Counter()`（<Term>コンポーネント</Term>と呼ぶ関数） | いまのデータから、画面のオブジェクトを作って返す |
| `let loans` | `useState(0)` が返す1つ目（`count`） | 画面を決めるデータ（<Term>state</Term>と呼ぶ） |
| `setLoans(next)` | `useState(0)` が返す2つ目（`setCount`） | データを新しい値に替えて、描き直してもらう |
| `h('p', null, …)` | `<p>…</p>`（前回の最後に見たJSX） | 画面のオブジェクトを書く。`{count}` のような波括弧の中には、JavaScriptの値を書ける |
| `render(view(), root)` | 描き直しのたびには呼ばない | Reactが、必要なときにコンポーネントを呼び直す |

`const [count, setCount] = useState(0)` は、Reactに「最初の値が 0 のデータを1つ、覚えておいてください」と頼むものです。値を覚えているのはReactで、コンポーネントの関数の外にあります。
ボタンを押すと `setCount(count + 1)` が呼ばれ、Reactが `Counter()` をもう一度呼びます。そのとき `useState` は、最初の 0 ではなく、Reactが覚えている 1 を返します。だから、返されるJSXも「1冊」に変わります。

`useState` のように、名前が `use` で始まるReactの関数を<Term>フック</Term>（Hooks）と呼びます。`<button onClick={関数}>` は、「このボタンが押されたら、この関数を呼ぶ」という意味です。
試しに、`useState(0)` の 0 を 5 に書き換えて、最初の表示が変わることを確かめてください。

ミニReactと違う点が1つあります。ミニReactの `loans` は、ずっと同じ1つの変数でした。Reactの `count` は、コンポーネントが呼ばれるたびに新しく作られる変数です。この違いが、今日の後半の主題になります。

前回の全体図でいえば、`setCount` が「きっかけ」、`Counter()` が呼び直されるのが「レンダー」です。

## JavaScriptにとって、「同じ」とは何か？

`Object.is(x, y)` は、`x` と `y` が「同じ」なら `true` を返す関数です。実行結果の表の式が、それぞれ `true` になるか `false` になるかを、予想してください（最後の1行だけは、数で答えます）。

<Sandbox spec={objectIsSandbox} />

<Question>
8つすべてに予想を立ててから、「答えを表示」を押してください。
予想と違ったのは、どれでしたか。配列やオブジェクトにとっての「同じ」は、何を比べているのでしょうか。
</Question>

<Reveal>

数や文字列は、値が同じなら「同じ」です。
配列やオブジェクトは違います。中身がまったく同じでも、別々に作ったものは「同じ」ではありません（表の上から4〜6番目）。`Object.is` が比べているのは中身ではなく、「同じ1つのものを指しているか」です。

`b = a` は、配列をコピーしません。同じ1つの配列に、`b` という2つ目の名前を付けるだけです。だから `a` に `push` すると、`b` から見ても1件増えています（最後の行）。そして、`push` のあとも `a` と `b` は同じ1つの配列なので、`Object.is(a, b)` は `true` のままです（表の7番目）。

変数が持っている、「どのオブジェクトを指しているか」という情報を<Term>参照</Term>と呼びます。`Object.is` は、配列やオブジェクトについては、参照が同じかどうかを比べます。

</Reveal>

## 1件だけ変えたいとき、全部作り直すのか？

一覧の中の1件だけを「返却済」にしたい場合を考えます。配列ごと新しくするなら、中の貸出も全部作り直すのでしょうか。

`updates.ts` の `returnLoan` は、指定した1件を返却済にした、新しい配列を返す関数です。`compareUpdates.ts` は、その前と後を1行ずつ `Object.is` で比べて、表にしています。
`compareUpdates.ts` の `returnLoan(before, 2)` の 2 を 3 に書き換えると、返却済にする貸出が変わります。

<Sandbox spec={compareUpdatesSandbox} />

<Question>
`returnLoan` の前と後で、「新しく作ったもの」になっているのはどれで、「同じもの」のままなのはどれでしょうか。
変えていない行まで新しく作り直さないのは、なぜだと思いますか。
</Question>

<Reveal>

新しく作ったのは、配列そのものと、状態を変えた「プロジェクター」の1件だけです。ほかの2件は、前と同じオブジェクトをそのまま使っています。

```ts
return loans.map((loan) => (loan.id === id ? { ...loan, status: 'returned' } : loan));
```

`map` が新しい配列を作ります。変える1件だけ、`{ ...loan, status: 'returned' }` で中身をコピーした新しいオブジェクトにして、ほかは `loan` をそのまま返しています。

変えていないものを同じままにしておくと、「どれが変わったか」が `Object.is` だけでわかります。中身を1つずつ見比べなくて済みます。
「同じものなら、中を見るまでもなく変わっていない」と言えることは、あとの回で、変わっていない部分の仕事を省くときに使います。

</Reveal>

## 関数は、いつの変数を見ているのか？

ループの中で、ボタンを3つずつ作りました。上の段と下の段の違いは、数える変数を `var` で作るか、`let` で作るかだけです。

<Sandbox spec={loopButtonsSandbox} />

<Question>

ボタンに書いてある番号は合っているのに、押したときの番号が違うのは、なぜでしょうか。
</Question>

<Reveal>

`var` のボタンは、どれを押しても「3番」と出ます。`let` のボタンは、自分の番号が出ます。

関数は、作られた場所から見えていた変数を、あとで呼ばれたときにも読めます。この仕組み（と、その関数）を<Term>クロージャ</Term>と呼びます。
大事なのは、関数が覚えているのは「そのときの値」ではなく、「どの変数か」だということです。

- `var i` は、ループ全体で1つの変数です。3つのボタンの関数は、同じ1つの `i` を見ています。ボタンが押されるのはループが終わったあとで、そのとき `i` は 3 になっています。
- `let j` は、ループの1周ごとに、新しい変数が作られます。3つの関数は、それぞれ別の `j` を見ていて、その `j` はあとから変わりません。

ボタンの文字（`var の 0 番`）が合っているのは、文字はループの途中でその場で作っているからです。その時点では `i` はまだ 0 でした。

</Reveal>

## 1秒ごとに増やすはずが、なぜ 1 で止まる？

最後に、もう1つ困りごとを見ます。「1秒ごとに `count` を1増やす」つもりで書いたコードです。

読むために必要なことは2つだけです。
`setInterval(関数, 1000)` は、渡した関数を1秒ごとに呼び続けます。
`useEffect(関数, [...])` は、「レンダーの結果が画面に反映されたあとで、この関数を実行してください」とReactに頼むものです。2つ目の `[...]`（依存配列）に入れた値が前回と変わらなければ、実行し直しません。関数が `return` で返している関数は、実行し直す前の後片づけ（ここではタイマーを止める）です。詳しくは第5回で扱います。

デモのコードのうち、`log.` で始まる行と1つ目の `useEffect` は、右側の履歴に記録するためのものです。読むのは、2つ目の `useEffect` だけでかまいません。

<StaleClosure />

最初は「バグ版」が動いています。右側には、レンダーごとの `count` が並びます。

<Question>
`count` は、いくつで止まりましたか。タイマーは止まっていません（「〜回呼ばれた」は増え続けています）。
コールバック（`setInterval` に渡した関数）は、`count` をいくつだと見ているでしょうか。それはなぜでしょうか。
</Question>

<Reveal>

`count` は 1 で止まります。

タイマーを作っているのは、レンダー#1 のあとに実行された関数です。依存配列に `count` が入っていないので、そのあと `count` が変わっても、タイマーは作り直されません。
`setInterval` に渡した関数は、レンダー#1 の `count`（0）を見続けます。1秒ごとに `setCount(0 + 1)` を呼んでいるので、何回呼ばれても、頼んでいるのは「1にしてください」です。2回目からは、いまの値と同じなので、画面は変わりません。

これは、Reactの不具合ではありません。さきほどのループや、3秒後のお知らせと同じ、クロージャの性質です。

</Reveal>

デモの残り3つのボタンは、直し方です。それぞれ押して、右側の履歴がどう変わるかを比べてください。

<Question>
「関数型更新」と「依存配列にcount」は、どちらも `count` が増え続けます。
右側の「タイマー」の行は、2つでどう違いますか。
</Question>

<Reveal>

| 書き方 | していること | タイマー |
|---|---|---|
| 関数型更新 | `setCount((current) => current + 1)`。`count` を読まず、「いまの値に1を足す」という計算のしかたを渡す | 1つのまま |
| 依存配列にcount | `count` が変わるたびに、タイマーを止めて、新しい `count` を見るタイマーを作り直す | 毎秒、作り直される |
| useEffectEvent版 | タイマーから呼ぶ関数だけを、「呼ばれた時点のいちばん新しい値を読める」特別な関数にする | 1つのまま |

「関数型更新」では、`setCount` に値ではなく関数を渡しています。Reactは、その時点のいちばん新しい値をこの関数に渡して、次の値を計算します。古い `count` を読まないので、古い回の関数が動き続けても困りません。
「次の値が、いまの値から決まる」ときは、この書き方がいちばん素直です。

残りの2つは、エフェクト（`useEffect`）の話に踏み込みます。どちらを選ぶかは、第5回で扱います。今日は、「3つとも、古い値を見続ける問題への、別々の答えである」ことだけ覚えておいてください。

</Reveal>

## 今日の要点

<Reveal label="要点を見る">

今日見たJavaScriptの性質は、2つです。

| JavaScriptの性質 | Reactで起きること | 書き方 |
|---|---|---|
| 配列やオブジェクトの「同じ」は、中身ではなく、同じ1つのものを指しているかで決まる | 書き換えた配列を `set` しても、「同じ」と判定されて描き直されない | 書き換えずに、新しい配列・オブジェクトを作って渡す |
| 関数は、作られたときに見えていた変数を見続ける | 古いレンダーで作られた関数は、古いstateを読む | 次の値がいまの値から決まるなら、`set` に関数を渡す |

Reactは、stateの中身を見張っているわけではありません。`set` 関数が呼ばれたときに、いまの値と次の値を `Object.is` で比べるだけです。
だから、「変えたこと」は、新しいものを作って渡すことで伝えます。

</Reveal>

## よくある誤解

<Misconception wrong="Reactは、stateの中身が変わったことを検知して、画面を描き直す。">

Reactは、中身を見張っていません。`set` 関数が呼ばれたときに、いまの値と次の値が「同じ」かどうか（配列やオブジェクトなら、同じ1つのものかどうか）を比べるだけです。配列に `push` しても、`set` に同じ配列を渡せば、何も起きません。

</Misconception>

<Misconception wrong="setCount を呼ぶと、count という変数が書き換わる。">

その回の `count` は、最後まで変わりません。`setCount` は、「次のレンダーでは、この値にしてください」と頼むだけです。新しい値が入った `count` は、次に呼ばれたときの、別の変数です。

</Misconception>

<Misconception wrong="古い値を読んでしまうのは、Reactの不具合だ。">

関数が、作られたときの変数を見続けるのは、JavaScriptのクロージャの性質です。`var` と `let` のループで見たことと、同じことが起きています。

</Misconception>
