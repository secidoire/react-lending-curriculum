## 検証ツールが見せているのは、図のどれ？

<Question>
Elements パネルに出ているのは、図のどの箱でしょうか。「ページのソースを表示」はどの箱でしょうか。
それが決まると、田中さんの2つの相談に答えられます。
</Question>

<Reveal>

Elements パネルが見せているのはDOMで、「ページのソースを表示」が見せているのは `index.html` です。この2つは別のものです。

- `<tbody>`：HTMLの決まりでは、表の行は `<tbody>` の中に入ります。書かれていなかったので、パースのときにブラウザが要素を補いました。
- `</p>`：同じくパースのときに、`<table>` の手前で段落が終わったものとして扱われました。Elements パネルは、できあがった木をHTMLの形に直して見せています。
- 件数の文字：ページが読み込んでいるJavaScript（`main.js`）が、DOMができたあとに書き換えました。
- リロードで元に戻る：田中さんが書き換えたのはDOMです。リロードすると、ブラウザは `index.html` をもう一度パースして、DOMを作り直します。

つまり、HTMLファイルはDOMの初期値にすぎません。画面は、ファイルからではなく、DOM（とCSSOM）から作られます。

冒頭の予想の答えも出ました。`index.html` を書き換えなくても、DOMを変更すれば画面の文字は変わります。そのとき `index.html` は1文字も変わっていません。

</Reveal>

## 色と幅で、光る範囲が違うのはなぜ？

Paint flashing は、ペイントし直した範囲を緑に光らせる機能です。色を変えたときは1行だけが、幅を変えたときは表全体が光りました。

DOMやスタイルを変更すると、ブラウザは図の途中の段階から、下に向かってもう一度計算します。

<Question>
色の変更と幅の変更で、やり直しになる段階はどう違うでしょうか。
</Question>

<Reveal>

どちらもCSSの変更なので、スタイル計算からやり直しになります。違うのは、その次です。

色を変えても、要素の大きさと位置は変わりません。レイアウトは飛ばせるので、その行をペイントし直すだけで済みます。

幅を変えると、レイアウトもやり直しになります。列の幅が変わると、同じ列のセルや隣の列の位置も変わるので、影響を受けた範囲がすべてペイントし直されます。

変更したときにかかる手間は、「どの段階がやり直しになり、どこまで影響が広がるか」で決まります。

</Reveal>

## 1000行の追加で、1つだけ遅いのはなぜ？

3つの方法は、どれも同じ1000個の行を表に追加しています。

<Question>
「1行ずつ追加」と「まとめて追加」の差は、予想と比べてどうでしたか。
「毎回高さを読む」だけが極端に遅いのは、追加のたびに図のどの段階が動いているからでしょうか。
</Question>

<Reveal>

ブラウザは、DOMを変更されても、その場ではレイアウトを計算しません。次に画面を描くときまで後回しにして、まとめて計算します。
だから、1行ずつ1000回追加しても、まとめて1回で追加しても、レイアウトの計算は1回で済みます。

ところが `offsetHeight`（要素の高さ）のような値は、最新のレイアウトがないと答えられません。
変更の直後に読むと、ブラウザはその場でレイアウトを計算します。これを1000回くり返したのが3つ目の方法です。

| 方法 | 表への追加 | レイアウトの計算 | 実測の例 |
|---|---|---|---|
| 1行ずつ追加 | 1000回 | 1回 | 約20ms |
| まとめて追加 | 1回 | 1回 | 約20ms |
| 1行ずつ追加し、毎回高さを読む | 1000回 | 1000回 | 約800ms |

実測はChromeでの一例で、数値はPCによって変わります。どの方法も、レイアウトの計算が終わるところまでを測っています（`measure.js` が最後にページの高さを読んでいるのは、そのためです）。

3つ目の方法では、行が増えるほど1回のレイアウトの計算も重くなります。それを1000回くり返すので、差は桁違いになります。

</Reveal>

## 模範解答の要点

<Reveal label="模範解答と要点を見る">

「まとめて追加」は、まだ画面につながっていない入れ物（<Term>DocumentFragment</Term>）に行を集めてから、1回で表に追加します。
今回の実験では、こうしても速くはなりませんでした。「1行ずつ追加」でも、レイアウトの計算は同じ1回だからです。

```js {2,6}
export function appendWithFragment(tbody, items) {
  const fragment = document.createDocumentFragment();
  for (const item of items) {
    fragment.append(createRow(item));
  }
  tbody.append(fragment);
}
```

今日の要点は3つです。

- HTMLファイルはDOMの初期値にすぎない。
- DOMを変更すると、レイアウトやペイントの再計算が走る。どこからやり直すかは、何を変えたかで決まる。
- 桁違いに遅くなるのは、DOMを変更する回数が多いときではなく、レイアウトの再計算が何度も走るとき。変更と読み取りを交互にくり返すと、そのたびに再計算が走る。

全体は `handson/part0/0-1-browser-dom/solution/` にあります。

</Reveal>

## よくある誤解

<Misconception wrong="DOM操作は常に遅い。">

表への追加は、1000回行っても、レイアウトの計算1回を含めて約20msでした。桁違いに遅くなるのは、レイアウトの再計算が何度も走るときです。変更と読み取りを交互にくり返すと、変更のたびに再計算が走ります。

</Misconception>

<Misconception wrong="Elements パネルで直せば、ファイルも直る。">

Elements パネルで書き換えているのはDOMです。ファイルは変わらないので、リロードすると元に戻ります。

</Misconception>
