## 検証ツールが見せているのは、図のどれ？

<Question>
さきほどの例の3つの枠は、それぞれ図のどれにあたるでしょうか。
それをもとに、田中さんの2つの相談（「どっちが本物？」「なぜ元に戻る？」）に、自分の言葉で答えてください。
</Question>

<Reveal>

Elements パネルが見せているのはDOMです。`index.html` は、DOMを作るもとになったファイルです。この2つは別のものです。

- `<tbody>`：HTMLの決まりでは、表の行は `<tbody>` の中に入ります。書かれていなかったので、パースのときにブラウザが要素を補いました。
- `</p>`：ファイルには `</p>` が書かれていません。HTMLの決まりでは、段落の中に表は入れられないので、パースのときに `<table>` の手前で段落が終わったものとして扱われました。Elements パネルは、できあがった木をHTMLの形に直して見せているので、閉じタグが見えます。
- 件数の文字：ページが読み込んでいるJavaScript（`main.js`）が、DOMができたあとに書き換えました。
- リロードで元に戻る：田中さんが書き換えたのはDOMです。リロードすると、ブラウザは `index.html` をもう一度パースして、DOMを作り直します。

つまり、HTMLファイルはDOMの初期値にすぎません。画面は、ファイルからではなく、DOM（とCSSOM）から作られます。

冒頭の予想の答えも出ました。`index.html` を書き換えなくても、DOMを変更すれば画面の文字は変わります。そのとき `index.html` は1文字も変わっていません。

</Reveal>

## 1000行を追加する。遅いのはどれ？

開発チームの先輩からも相談が来ました。
「備品が1000件になったら、一覧の表示が遅くなりそう。DOMを触るのは遅いって聞くけど、本当に遅いのはどこなのか知りたい。」

表に1000行を追加する方法を、3つ用意しました。コードに出てくる名前は、次のとおりです。

- `items`：追加する1000件のデータ。
- `tbody`：表の行を入れる要素。`tbody.append(行)` で、行が表の最後に足されます。
- `createRow(item)`：1件のデータから行（`<tr>`）を作る関数。

```ts
// 方法1：1行ずつ、表に追加する。
for (const item of items) {
  tbody.append(createRow(item));
}
```

```ts
// 方法2：行をすべて作ってから、1回の操作で表に追加する。
const fragment = document.createDocumentFragment();
for (const item of items) {
  fragment.append(createRow(item));
}
tbody.append(fragment);
```

```ts {5}
// 方法3：1行ずつ追加し、追加するたびに表の高さを読む。
for (const item of items) {
  tbody.append(createRow(item));
  // 読んだ値は使わない。読むことだけが目的。
  void tbody.offsetHeight;
}
```

方法2の `fragment` は、まだ画面につながっていない入れ物です。行をここに集めてから、最後に1回で表に追加します。
方法3の `tbody.offsetHeight` は、表の高さ（ピクセル数）です。先頭の `void` は「この値は使わずに捨てる」という意味で、方法1との違いはこの1行だけです。

<Question>
測る前に、遅い順を予想してください。
予想できたら、実行結果の中のボタンをそれぞれ3回ずつ押して確かめます。
</Question>

<Sandbox spec={benchmarkSandbox} />

3つの方法は `appendRows.ts` に書いてあります。読む値を変えたり、行数を変えたりして、結果がどう変わるかを試せます。

<Question>
結果は、予想と比べてどうでしたか。
方法1と方法3の違いは、高さを読む1行だけです。読むだけで、なぜこれほど変わるのでしょうか。
</Question>

<Reveal>

ブラウザは、DOMを変更されても、その場ではレイアウトを計算しません。実行中のJavaScriptが一区切りついて、次に画面を描くときまで後回しにして、まとめて計算します。
だから、1行ずつ1000回追加しても、まとめて1回で追加しても、レイアウトの計算は1回で済みます。

ところが `offsetHeight`（要素の高さ）のような値は、最新のレイアウトがないと答えられません。
変更の直後に読むと、ブラウザはその場でレイアウトを計算します。これを1000回くり返したのが方法3です。

| 方法 | 表への追加 | レイアウトの計算 | 実測の例 |
|---|---|---|---|
| 方法1：1行ずつ追加 | 1000回 | 1回 | 約20ms |
| 方法2：まとめて追加 | 1回 | 1回 | 約20ms |
| 方法3：1行ずつ追加し、毎回高さを読む | 1000回 | 1000回 | 約850ms |

実測はChromeでの一例で、数値はPCによって変わります。どの方法も、後回しにされたレイアウトの計算が終わるところまでを測っています。

方法3では、行が増えるほど1回のレイアウトの計算も重くなります。それを1000回くり返すので、差は桁違いになります。

方法2の入れ物を<Term>DocumentFragment</Term>と呼びます。今回の実験では、これを使っても速くはなりませんでした。方法1でも、レイアウトの計算は同じ1回だからです。

</Reveal>

## 今日の要点

<Reveal label="要点を見る">

- HTMLファイルはDOMの初期値にすぎない。画面は、DOM（とCSSOM）から作られる。
- DOMやスタイルを変更すると、図の途中の段階からやり直しになる。どの段階がやり直しになるかは、何を変えたかで決まる（色ならレイアウトは飛ばせる。幅ならレイアウトからやり直す）。
- 桁違いに遅くなるのは、DOMを変更する回数が多いときではなく、レイアウトの再計算が何度も走るとき。DOMの変更と、高さや位置の読み取りを交互にくり返すと、そのたびに再計算が走る。

</Reveal>

## よくある誤解

<Misconception wrong="DOM操作は常に遅い。">

表への追加は、1000回行っても、レイアウトの計算1回を含めて約20msでした。桁違いに遅くなるのは、レイアウトの再計算が何度も走るときです。DOMの変更と、高さや位置の読み取りを交互にくり返すと、変更のたびに再計算が走ります。

</Misconception>

<Misconception wrong="Elements パネルで直せば、ファイルも直る。">

Elements パネルで書き換えているのはDOMです。ファイルは変わらないので、リロードすると元に戻ります。

</Misconception>
