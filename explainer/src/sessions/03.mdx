## 前回の予告を確かめよう

総務の田中さんから、依頼が来ました。「備品を選んで、借りる人と、借りる期間（いつから・いつまで）を入力して、貸出を登録できるようにしてください。」

<Question>
フォームには、利用者が好きなように入力できます。日付の欄が空のまま送信されるかもしれません。
入力された値が正しいかどうかは、どこで確かめることになるでしょうか。TypeScriptの型は、それを確かめてくれるでしょうか。予想を決めてから、先へ進みます。
</Question>

## 何も入力せずに登録すると、何が起きる？

フォームを作りました。前回の「制御されたコンポーネント」の形で、4つの欄の値を1つの state（`values`）に持っています。
「貸出を登録」を押すと、`<form>` の `onSubmit` に渡した関数（`submit`）が呼ばれ、入力された値を一覧に足します。

<Sandbox spec={lendFormNoCheckSandbox} />

`submit` の最初にある `event.preventDefault()` は、フォームのもともとの動き（送信してページを読み込み直す）を止めるためのものです。このフォームでは、送信されたときの処理を自分で書くので、もとの動きは止めます。

<Question>
次の2つを試してください。それぞれ、一覧には何と表示されましたか。

1. 何も入力せずに、「貸出を登録」を押す。
2. 「いつから」に10月12日、「いつまで」に10月10日を入れて、登録する。

このコードは、TypeScriptの型チェックを通っています。それなのに、なぜこうなるのでしょうか。
</Question>

<Reveal>

1では「（備品なし）：さん、Invalid Date 〜 Invalid Date（NaN日間）」、2では「-1日間」という貸出が、そのまま登録されます。空の文字列を日付として読もうとした結果が `Invalid Date` で、それを使った計算の結果が `NaN`（数ではない）です。

`Loan` の型は `{ itemId: string; userName: string; from: string; to: string }` です。空の文字列 `''` も、前後が逆の日付も、どちらも `string` です。型の上では、何も間違っていません。

TypeScriptの型が確かめるのは、「コードの中で、値の受け渡しのつじつまが合っているか」です。確かめるのはコードを書いているときで、アプリが動いている間は、型は何もしません。
利用者が実際に何を入力するかは、動かしてみるまでわかりません。型は、「日付として読める文字列である」「いつまでは、いつから以降である」といった中身の正しさまでは守れません。

</Reveal>

入口で1回だけ確かめれば、その先のコードは「ここに届いた値は正しい」と信じて書けます。`formatDate` や `daysOfPeriod` の中で、「空だったら」「逆だったら」を心配する必要がなくなります。

1つ、正直に言っておくことがあります。確かめ終わった値（`LendRequest`）も、TypeScriptの型としては、文字列が4つ入ったオブジェクトです。中身の正しさを保証しているのは型そのものではなく、「`LendRequest` を作る入口は、確かめる関数だけにする」という約束です。入口を1つにしておくことが大事です。

フォームのように、アプリの外から値が入ってくる場所を、<Term>境界</Term>と呼びます。あとの回で出てくる、保存したデータの読み込みや、サーバーからの返事も境界です。

## 「正しい形」を、どう書く？

確かめる処理を、`if` を並べて手で書くこともできます。ここでは、zod というライブラリを使います。「正しい形」を宣言として書いたものを、<Term>スキーマ</Term>と呼びます。

下の枠の `lendFormSchema.ts` を開いてください。読むのは、上半分（`LendFormSchema` と `LendRequest` まで）です。下半分の `parseLendForm` は、確かめた結果を「どの欄が、なぜだめか」の形に並べ替えているだけなので、いまは読み飛ばしてかまいません。

<Sandbox spec={lendPageSandbox} />

- `z.object({ ... })`：「この名前の項目を持つオブジェクト」という形。
- `z.string().min(1, 'メッセージ')`：1文字以上の文字列。だめなときのメッセージを添えられます。
- `.trim()`：前後の空白を取り除いてから確かめます。
- `z.iso.date('メッセージ')`：`2026-10-12` の形で、実際にある日付を表す文字列。確かめたあとも、文字列のままです。
- `.refine(関数, { path, message })`：項目どうしの関係など、上の書き方では表せない条件を足します。`path` は、どの欄の問題として伝えるかです。`2026-10-12` の形の文字列は、文字列のまま `<=` で比べても、日付の前後と同じ結果になります。
- `LendFormSchema.safeParse(値)`：値を確かめます。正しければ `{ success: true, data }`、だめなら `{ success: false, error }` を返します。`data` は、空白を取り除くなどの変換を済ませた値です。

`LendForm.tsx` の `<form … noValidate>` は、ブラウザが自分で出す入力チェックの吹き出しを止めるためのものです。代わりに、自分で用意したメッセージを欄の下に出します。

<Question>
最初の枠で試した2つ（何も入力しない／日付が逆）を、この枠でも試してください。今度は、どうなりましたか。
`lendFormSchema.ts` の `LendRequest` という型は、どうやって作られているでしょうか。型を別に手で書かないのは、なぜだと思いますか。
</Question>

<Reveal>

どちらも登録されず、問題のある欄の下に理由が出ます。一覧に届くのは、確かめ終わった値だけです。

`LendForm.tsx` の `submit` が境界です。

```tsx
const result = parseLendForm(values);
if (!result.ok) {
  setErrors(result.errors);
  // …（フォーカスを移す）
  return;
}

onLend(result.request);
```

`parseLendForm` の引数の型は `unknown` です。「何が来るかわからない」ことを、型でも正直に表しています。正しいとわかった場合だけ、`LendRequest` 型の値が取り出せます。

`LendRequest` は、`z.infer<typeof LendFormSchema>` で、スキーマから導いています。
型を別に手で書くと、「スキーマでは必須なのに、型では省略できる」のように、2つが食い違うことがあります。これも、同じ情報を2か所に持つ問題です。スキーマを1つだけ書き、型はそこから導けば、食い違いは起きません。

</Reveal>

## エラーのとき、カーソルはどこへ行く？

もう一度、上の枠で、何も入力せずに「貸出を登録」を押してください。

<Question>
押したあと、キーボードのカーソル（フォーカス）は、どこにありますか。
「この欄にフォーカスを移す」は、これまでのように「state を変えて、画面を描き直す」ことで実現できるでしょうか。
</Question>

<Reveal>

フォーカスは、最初に問題のあった欄（「備品」）に移っています。利用者は、すぐに直し始められます。

フォーカスを移すのは、「画面がどうあるべきか」ではなく、「いま、これをしてほしい」という命令です。state とJSXでは書けません。DOMの要素を直接つかまえて、`focus()` を呼ぶ必要があります。
そのための道具が<Term>ref</Term>です。

```tsx
const userRef = useRef<HTMLInputElement>(null);
// …
<input ref={userRef} … />
// …
userRef.current?.focus();
```

`useRef(null)` は、`{ current: null }` という入れ物を作ります。この入れ物は、再レンダーされても同じものが使い続けられ、中身を書き換えても再レンダーは起きません。
JSXの `ref={userRef}` に渡しておくと、Reactは、その入力欄が画面に出たときに、DOMの要素を `userRef.current` に入れてくれます（それまでは `null` なので、`?.` を付けて呼んでいます）。
これで、イベントハンドラの中から、本物のDOMの要素に手が届きます。

ref は、Reactの「state から画面を作る」仕組みの外に出るための抜け道です。フォーカス、スクロール、大きさの計測のように、state とJSXでは表せないことにだけ使います。表示する文字や、要素を出す・消すを ref で直接書き換えることはしません。それは state の仕事です。

</Reveal>

## ラベルと入力欄は、どう結びつける？

`FormField.tsx` と `LendForm.tsx` を見てください。ラベルの `htmlFor` と、入力欄の `id` に、同じ値を入れています。こうすると、ラベルを押したときに入力欄へフォーカスが移り、読み上げソフトも「どのラベルの欄か」を伝えられます。

最初の枠では、`id="userName"` のように、決まった文字を書いていました。

<Question>
`id` は、1つのページの中で重ならないことになっています。
最初の枠のフォームを、同じページに2つ置いたら、何が起きるでしょうか。
</Question>

<Reveal>

`id="userName"` の入力欄が2つできてしまいます。2つ目のフォームのラベルを押しても、1つ目のフォームの入力欄にフォーカスが移ります。

コンポーネントは、何度でも使い回せることに意味があります。使われるたびに重ならない `id` が必要です。`useId` は、そのコンポーネントが置かれた場所ごとに、重ならない文字列を作るフックです。

```tsx
const id = useId();
// …
<FormField label="借りる人" inputId={`${id}-userName`} error={errors.userName}>
  <input ref={userRef} id={`${id}-userName`} … />
</FormField>
```

`<FormField>…</FormField>` の間に書いた入力欄は、`children` という名前の props として `FormField` に届きます。`FormField` は、ラベルとエラーの文の間に、受け取った `children` を置いています。

</Reveal>

## 今日の要点

<Question>
レビューの問いです。「貸出は最長14日まで」という決まりを足すことになりました。
この決まりは、入力欄（選べる日付を制限する）、スキーマ、貸出を実際に作る処理、のどこに書くのがよいでしょうか。
</Question>

<Reveal label="答えと要点を見る">

スキーマに `.refine` を1つ足せば、14日を超える貸出は登録できなくなります。`lendFormSchema.ts` の先頭で `import { daysOfPeriod } from './period';` を足し、いまある `.refine(...)` のうしろに、次の1つをつなげます。

```ts
.refine((value) => daysOfPeriod(value.from, value.to) <= 14, {
  path: ['to'],
  message: '借りられるのは14日間までです',
});
```

いまの規模なら、これで足ります。

ただ、「日付として読めるか」と「最長14日」は、性質が違います。前者は、入力の形の正しさです。後者は、貸出という仕事の決まりで、フォーム以外から貸出を作るとき（次回の「予約から貸出にする」など）にも守る必要があります。
仕事の決まりは、フォームのスキーマではなく、貸出を作る関数の側に置くほうが、入口が増えても守られます。「入力の形は境界で1回だけ確かめる」ことと、「仕事の決まりは、その仕事をする関数が守る」ことは、別の話です。この分け方は、次回から扱います。
入力欄で選べなくするのは、利用者への親切です。それだけに頼ることはできません。入力欄を通らずに値が来ることもあるからです。

- 利用者が入力した値は、型では守れない。動いているときに、確かめる必要がある。
- 確かめるのは、境界で1回だけ。その先は、正しい値だけが流れる。
- スキーマを1つ書き、型はそこから導く。
- フォーカスのような「命令」は、ref でDOMの要素をつかまえて行う。

</Reveal>

## よくある誤解

<Misconception wrong="TypeScriptの型があれば、動いているときの確認は要らない。">

型が守るのは、コードの中のつじつまです。利用者の入力、保存したデータ、サーバーからの返事のように、外から来る値は、動いているときに確かめるしかありません。

</Misconception>

<Misconception wrong="入力欄に required や type=&quot;date&quot; を付けておけば、確認は済んでいる。">

入力欄の属性は、利用者が間違えにくくするためのものです。入力欄を通らずに値が来ること（別の画面、保存したデータ、サーバー）もあり、そこでは効きません。確かめる処理は、自分のコードの境界に置きます。

</Misconception>

<Misconception wrong="ref を使えば、state を使わずに画面を書き換えられて手軽だ。">

ref でDOMを書き換えると、Reactが知っている画面と、実際のDOMが食い違います。次のレンダーで、書き換えが消えたり、ずれたりします。ref は、フォーカスのような、state では表せないことにだけ使います。

</Misconception>
