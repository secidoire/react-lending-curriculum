## なぜ、ありえない状態を作れてしまう？

上の枠の「コードを見る」を開いて、`Loan` の型を読んでください。

```ts
type Loan = {
  id: string;
  itemName: string;
  userName: string;
  status: string;
  dueDate?: string;
  returnedAt?: string;
  overdue?: boolean;
};
```

`?` の付いた項目は、「あってもなくてもよい」という意味です。

<Question>
この型は、次のような値を許すでしょうか。

- `status` が `'returned'` で、`returnedAt` がない。
- `status` が `'returned'` で、`overdue` が `true`。
- `status` が `'reservd'`（つづりの間違い）。

見つけたバグは、それぞれ、どこから来ているでしょうか。
</Question>

<Reveal>

3つとも、許してしまいます。`status` の型が `string` なので、どんな文字列でも通ります。型が許している値は、コードのどこかで、うっかり作られてしまいます。

- **返却日がない・延滞が残る**：`status` と、`returnedAt` や `overdue` が、別々の項目になっています。「返却済なら、返却日が必ずある」という関係が、型のどこにも書かれていません。返却の処理が `status` だけを書き換えても、型は何も言いません。
- **延滞が出ない・残る**：延滞かどうかは、期限と今日の日付から計算できます。計算できるものを `overdue` として持っているので、誰かがボタンを押して合わせ直すまで、古いままです。第2回の派生データと同じ問題です。
- **予約中からいきなり返却**：「どの状態から、どの状態へ変われるか」という決まりが、どこにも書かれていません。ボタンの処理が、好きなように `status` を書き換えています。
- **改名が反映されない**：貸出が、備品の名前のコピー（`itemName`）を持っています。同じ情報が2か所にあるので、片方を変えても、もう片方は古いままです。

どれも、これまでの回で見てきた「同じ情報を2か所に持つ」「関係が書かれていない」の、データの形での現れです。

</Reveal>

## 状態ごとに、持つものを変えられないか？

<Question>
「予約中の貸出」「貸出中の貸出」「返却済の貸出」は、それぞれ、どんな項目を必ず持っているべきでしょうか。持っていてはいけない項目は、どれでしょうか。
3つを、別々の型として書いてみると、どうなるでしょうか。
</Question>

<Reveal>

状態ごとに型を分け、「貸出とは、この3つのうちのどれか」と書きます。

```ts
type LoanBase = { id: string; itemId: string; userName: string };

export type Loan =
  | (LoanBase & { status: 'reserved'; reservedFrom: IsoDate; reservedTo: IsoDate })
  | (LoanBase & { status: 'lent'; lentAt: IsoDate; dueDate: IsoDate })
  | (LoanBase & { status: 'returned'; lentAt: IsoDate; dueDate: IsoDate; returnedAt: IsoDate });
```

`|` は「または」、`&` は「両方の項目を持つ」です。`LoanBase` は、3つの状態に共通の項目です。`IsoDate` は、`2026-10-20` の形の文字列に付けた名前です。
`status: 'reserved'` は、「`'reserved'` という文字列だけを許す」という型です。`string` と違って、ほかの文字列は入りません。

こう書くと、「返却済なのに `returnedAt` がない」値は、型エラーになって書けません。`overdue` という項目は、そもそもどこにもありません。`'reservd'` も、3つのどれにも当てはまらないので書けません。
ありえない状態を、あとから確かめて弾くのではなく、コードの中では最初から書けなくしています。
（型が守るのは、自分たちのコードの中だけです。保存したデータやサーバーの返事のように、外から来る値は、前回のように境界でスキーマを使って確かめます。）

`status` のように、どの形かを見分ける項目を持たせた「または」の型を、<Term>判別可能なユニオン型</Term>と呼びます。`loan.status === 'lent'` と確かめると、TypeScriptは、その先で `loan.dueDate` があると理解します。確かめる前に `loan.dueDate` と書くと、型エラーになります。

なお、このページの枠は、型チェックをせずにコードを動かしています。枠の中で型に合わないコードを書いても、型エラーは表示されません。ふだんの開発では、エディタが、書いたその場で赤い波線で知らせます。

</Reveal>

## 状態の変え方は、どこに書く？

型で、「どんな値がありうるか」は決まりました。次は、「どの状態から、どの状態へ変われるか」です。
下の枠の `loan.ts` を開いてください。読むのは、`lend`・`returnLoan`・`isOverdue` の3つの関数です。

<Sandbox spec={loanBoardSandbox} />

<Question>
最初の枠で見つけた「ありえない表示」を、この枠でも起こそうとしてみてください。起こせましたか。
`returnLoan` は、貸出中でない貸出を渡されたとき、どうするでしょうか。`isOverdue` は、なぜ「今日」を引数で受け取っているのでしょうか（関数の中で `new Date()` を呼べば、引数は要らないはずです）。
</Question>

<Reveal>

どれも起こせません。

- 「延滞」は、最初から、期限を過ぎた貸出中のものにだけ出ています。確認するボタンはありません。返却すれば、消えます。
- 返却すると、必ず返却日が入ります。`returnLoan` が作る返却済の値には、`returnedAt` がないと型エラーになるからです。
- 改名は、貸出の一覧にも反映されます。貸出は名前を持たず、`itemId` から、いまの名前を引いているからです。同じ情報を1か所にしか持たないこの形を、<Term>正規化</Term>と呼びます。

`returnLoan` は、貸出中でなければ、`{ ok: false, reason: '…' }` を返して、何も変えません。予約中の行に「返却する」ボタンが出ていないのは、利用者への親切です。決まりを守っているのは、ボタンではなく、この関数です。

`isOverdue` が「今日」を引数で受け取るのは、純粋関数にしておくためです。中で `new Date()` を呼ぶと、同じ貸出を渡しても、実行した日によって結果が変わってしまいます。引数で受け取れば、同じ引数なら、いつも同じ結果です。「期限の翌日なら延滞」を確かめるテストも、好きな日付を渡すだけで書けます。
この3つの関数は、Reactと関係がありません。値を受け取って、値を返すだけの純粋関数です。

なお、「期限を過ぎてから返された」という事実そのものは、ありえます。良い版では、それも `returnedAt` と `dueDate` を比べれば計算できます。おかしかったのは、計算せずに持っていた `overdue` が、古いまま残ったことです。

</Reveal>

## 画面からは、何を伝える？

`LoanBoard.tsx` を開いてください。`useState` の代わりに、`useReducer` を使っています。

```tsx
const [state, dispatch] = useReducer(loansReducer, { loans: initialLoans, error: null });
// …
onReturn={() => dispatch({ type: 'returned', loanId: loan.id, today: TODAY })}
```

| | `useState` | `useReducer` |
|---|---|---|
| 画面が渡すもの | 次の値そのもの（`setLoans(次の配列)`） | 何が起きたか（`dispatch({ type: 'returned', … })`） |
| 次の値を決める場所 | イベントハンドラの中 | `loansReducer`（1つの関数） |

`dispatch` に渡す、「何が起きたか」を表す値を<Term>アクション</Term>と呼びます。`loansReducer(いまのstate, アクション)` が、次の state を返します。この関数を<Term>リデューサ</Term>と呼びます。

- `useReducer(リデューサ, 最初のstate)` は、`useState` と同じように、いまの state と、それを変えるための関数（`dispatch`）を返します。
- `dispatch(アクション)` を呼ぶと、Reactが、いまの state とそのアクションをリデューサに渡します。返ってきた値が次の state になり、再レンダーされます。
- アクションの `type` の `'lent'` は、「貸出された」という出来事の名前です。次の状態を直接指定しているわけではありません。どの状態になるかは、リデューサが決めます。
- state を `{ loans, error }` というオブジェクトにしたのは、できなかった操作の理由（`error`）も、貸出と一緒に決まるからです。

<Question>
`loansReducer.ts` を読んでください。「予約中のものを返却しようとした」とき、リデューサは何を返すでしょうか。
`LoanRow.tsx` の `{loan.status === 'lent' && (` を `{true && (` に書き換えると、予約中の行にも「返却する」が出ます。押すと、どうなるでしょうか。
</Question>

<Reveal>

予約中の行の「返却する」を押しても、貸出は変わらず、「返却できるのは、貸出中のものだけです」と表示されます。

リデューサは、対象の貸出を探し、`loan.ts` の関数（`lend` か `returnLoan`）を呼びます。できなかったときは、貸出を変えずに、理由だけを state に入れます。
決まりそのものは `loan.ts` にあり、リデューサはそれを呼ぶだけです。画面は、起きたことを伝えるだけです。

最初の枠のバグを防いでいるのは、型と、`loan.ts` の関数です。`useState` のままでも、イベントハンドラが必ず `loan.ts` の関数を通るなら、決まりは守れます。ただ、`setLoans` には好きな値を渡せるので、関数を通らずに書き換える道が残ります。
`useReducer` にすると、貸出の state を変える道が、リデューサの1本だけになります。「どう変わるか」を知りたければ、`loan.ts` と `loansReducer.ts` だけを読めば足ります。
リデューサも、Reactと関係のない純粋関数です。「この state に、このアクションが来たら、こうなる」を、画面なしでテストできます。

</Reveal>

## 今日の要点

<Question>
レビューの問いです。「予約をキャンセルできるようにしてほしい」と言われました。`Loan` の型に、4つ目の `{ status: 'cancelled'; … }` を足すとします。
先に、実験を1つします。上の枠の `initialLoans.ts` で、1件目の `status: 'reserved'` を `status: 'cancelled'` に書き換えてください。実行結果に、どんなエラーが出ましたか。

そのエラーを出したのは、`loan.ts` の `describeLoan` の `default` にある `assertNever(loan)` です。`assertNever` の引数の型 `never` は、「ここに来る値は、1つもないはず」という意味の型です。
これをもとに考えてください。型に4つ目の状態を足したあと、直さなければならない場所を、TypeScriptは教えてくれるでしょうか。
</Question>

<Reveal label="答えと要点を見る">

`switch` と `assertNever` を書いてある場所については、教えてくれます。
`describeLoan` の `switch` には、3つの状態の `case` があります。`case` を1つ通るたびに、TypeScriptは「残りの候補」を減らしていきます。3つとも書いてあれば、`default` に来る値は残っていないので、`never` を受け取る `assertNever(loan)` に渡せます。
4つ目の状態を足すと、`default` に `cancelled` の貸出が来うるので、`never` には渡せず、型エラーになります。「ここに `case` を足してください」と、コンパイラが教えてくれるわけです。

さきほどの実験では、枠が型チェックをしないので、動かしてから `assertNever` がエラーを出しました。ふだんの開発では、動かす前に、エディタが型エラーとして知らせます。

`if (loan.status !== 'lent')` のように `if` で書いた場所や、キャンセルのための関数やボタンが足りないことは、教えてくれません。だから、状態で分ける処理は、`switch` と `assertNever` で書いておきます。

- 状態ごとに型を分けて、ありえない組み合わせを書けなくする。
- 計算できるもの（延滞）は、持たずに計算する。同じ情報（備品の名前）は、1か所にだけ持つ。
- 「どう変われるか」の決まりは、Reactと関係のない関数に集める。画面は、起きたことを伝えるだけにする。

</Reveal>

## よくある誤解

<Misconception wrong="useReducer は、大規模なアプリのためのものだ。">

目的は規模ではありません。state の変え方の決まりを、1か所に集めることです。小さな画面でも、「この状態からは、この操作しかできない」という決まりがあるなら、役に立ちます。決まりのない単純な値なら、`useState` で十分です。

</Misconception>

<Misconception wrong="項目を省略可能（?）にしておけば、どんな場合にも対応できて柔軟だ。">

省略可能な項目が増えるほど、型が許す組み合わせが増えます。その多くは、ありえない組み合わせです。それを作らないように気をつける仕事が、コードのあちこちに生まれます。

</Misconception>

<Misconception wrong="延滞は状態の1つなので、status に 'overdue' を足せばよい。">

延滞は、誰も操作しなくても、時間が経つだけで始まります。`status` に持たせると、誰かが書き換えるまで、古いままになります。期限と今日の日付から、レンダーのたびに計算します。

</Misconception>
