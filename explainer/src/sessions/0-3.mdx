## 画面を、DOMを作る前に「データ」で書けないか？

必要なところとは、「1つ前に描いた画面」と「これから描く画面」で、違っているところです。それを知るには、2つを見比べたくなります。
ところが、0-2のB版の `render()` は、いきなりDOMの要素を作っていました。作る前に見比べる材料が、手元にありません。

そこで、DOMを作る前に、「こういう画面にしたい」という内容を、ただのオブジェクトで書くことにします。

下の `firstTree.ts` を読んでください。`h()` は、今日これから作る小さなライブラリ（`miniReact.ts`）の関数です。
引数は順に、要素の種類、属性、そのあとに子を好きな数だけ並べます。

<Sandbox spec={firstTreeSandbox} />

<Question>
実行結果の下半分に出ているのは、`h()` が返したものの中身です。`type`・`props`・`children` は、それぞれ `h()` のどの引数から来ているでしょうか。
次に、`root.append(createDom(tree));` の行を消すと、実行結果はどうなるでしょうか。予想してから、実際に消してみてください。
</Question>

<Reveal>

`h()` は、1つ目の引数を `type`（要素の種類）、2つ目を `props`（属性）、3つ目以降を `children`（子）に入れた、ただのオブジェクトを返すだけです。
子の中にまた `h()` があるので、全体は入れ子になった木の形になります。

`createDom` の行を消すと、文は出なくなり、オブジェクトの中身だけが残ります。`h()` を呼んでも、画面は何も変わらないからです。
画面に文を出していたのは、`createDom(tree)` でオブジェクトを本物のDOMに変え、`root.append()` で画面に入れる行でした。`createDom` は、`miniReact.ts` のタブにあります。

```ts
export function createDom(node: Child): Node {
  if (typeof node === 'string') return document.createTextNode(node);

  const dom = document.createElement(node.type);
  for (const [key, value] of Object.entries(node.props)) setProp(dom, key, value);
  for (const child of node.children) dom.append(createDom(child));
  return dom;
}
```

`Child` は「仮想ノードか、文字」という型です。文字ならテキストを作り、要素なら、属性を付けてから、子を1つずつ同じ関数でDOMにして中に入れています。
`setProp` は、属性を1つDOMの要素に設定する関数です（同じタブにあります）。

画面の要素を表すこのオブジェクトを<Term>仮想ノード</Term>、それが作る木を<Term>仮想DOM</Term>と呼びます。本物のDOMではなく、「こういうDOMがほしい」という注文書のようなものです。

</Reveal>

## 画面をデータから書くと、何が変わる？

0-2のB版の貸出一覧を、`h()` で書き直しました。今日は、削除の代わりに「状態を切り替える」と「先頭に1件追加」で確かめます。
0-2の `render()` がしていた仕事は、2つに分かれます。画面のオブジェクトを作る `view()`（`app.ts`）と、それをDOMにする `render`（`miniReact.ts`）です。

`app.ts` の中の3つを見てください。

- `view()`：いまのデータ（`loans`）から、画面全体を表すオブジェクトを作る関数。DOMには触りません。
- `setLoans(next)`：データを新しいものに替えて、`render(view(), root)` で画面を描き直す関数。
- `addToTop()` と `toggleStatus(id)`：操作の処理。新しいデータを作って `setLoans` に渡すだけです。

<Question>
「リーダブルコード」のメモ欄に文字を入れてから、ほかの行の「状態を切り替える」を押してください。メモはどうなりましたか。
0-2のB版と比べて、良くなったことと、まだ直っていないことは何でしょうか。
</Question>

<Reveal>

メモは消えます。まだ直っていません。`miniReact.ts` の `render` が、0-2のB版と同じように、全部を捨てて作り直しているからです。

```ts

```

良くなったことは2つあります。
1つは、`app.ts` からDOMを直接操作するコードが消えたことです。アプリが書くのは、「データがこうなら、画面はこう」という `view()` だけになりました。
もう1つは、画面がオブジェクトになったので、1つ前に描いた画面と、これから描く画面を、DOMを作る前に見比べられるようになったことです。

</Reveal>

`miniReact.ts` を、デモの右側と同じ「違うところだけ直す」ものに差し替えました（その2）。`app.ts` は、1文字も変えていません。

<Question>
さっきと同じ操作（メモ欄に入力 → ほかの行の「状態を切り替える」）をしてください。メモはどうなりましたか。

</Question>

<Reveal>

メモは残ります。

`app.ts` を変えずに済んだのは、アプリが書いているのが「データがこうなら、画面はこう」という `view()` だけだからです。DOMのどこをどう直すかは、ミニReactの中に閉じ込められています。

これで、0-2の2つの版のよいところが両立しました。アプリは、B版のようにデータだけを直します。DOMは、A版のように必要なところだけが直ります。DOMの直し忘れは、アプリの側では起きようがありません。

「いまの状態から、あるべき画面を書く」というこの書き方を<Term>宣言的UI</Term>と呼び、よく UI = f(state) と書き表します。

</Reveal>

では、ミニReactの中では何をしているのでしょうか。上の枠の `miniReact.ts` のタブを開き、`update` という関数を探してください。
`update` は、前回のオブジェクト（`oldNode`）と今回のオブジェクト（`newNode`）を受け取ります。`dom` は、前回のオブジェクトから作ったDOMです。

<Question>
`update` の中は、3つの場合に分かれています。それぞれ、どんな場合に、DOMに何をしているでしょうか。
3つのうち、メモが残ることに効いているのは、どれでしょうか。
</Question>

<Reveal>

```ts
function update(parent: Node, dom: Node, oldNode: Child, newNode: Child): void {
  // どちらも文字：違っていたら文字だけ書き換える。
  if (typeof oldNode === 'string' && typeof newNode === 'string') {
    if (oldNode !== newNode) dom.textContent = newNode;
    return;
  }
  // 種類が違う（div → p、要素 → 文字 など）：使い回せないので、作り直して置き換える。
  if (typeof oldNode === 'string' || typeof newNode === 'string' || oldNode.type !== newNode.type) {
    parent.replaceChild(createDom(newNode), dom);
    return;
  }
  // 種類が同じ：DOMはそのまま使い、変わった属性と子だけ直す。
  if (dom instanceof HTMLElement) updateProps(dom, oldNode.props, newNode.props);
  updateChildren(dom, oldNode.children, newNode.children);
}
```

メモが残ることに効いているのは、3つ目です。前回と今回で要素の種類が同じなら、DOMの要素は作り直さずに、そのまま使います。入力欄も同じ要素のままなので、打った文字が残ります。

`updateProps` は、前回と今回の属性を比べて、違うものだけをDOMに書く関数です。
`updateChildren` は、子を先頭から順に、同じ位置のものどうしで、また `update` に渡します。こうして木を下までたどります。

`render` は、前回描いたオブジェクトを覚えておき、2回目からは `update` を呼びます。
前回と今回の画面を見比べて、DOMに必要な変更を割り出すこの作業を、Reactでは<Term>差分検出</Term>（reconciliation）と呼びます。

</Reveal>

## どれとどれが同じかを、どう伝える？

ミニReactを完成版に差し替えました。完成版は、行に「目印」が書いてあれば、位置ではなく目印が同じものどうしを対応づけます。
この目印を `key` と呼びます。`app.ts` には、まだ `key` を書いていません。

<Sandbox spec={keyedSandbox} />

`app.ts` の `view()` の中に、行を作っている次の部分があります。

```ts
h(
  'tr',
  null,
```

この `null` を `{ key: loan.id }` に書き換えてから、さっきの操作（メモ欄に入力 → 「先頭に1件追加」）をもう一度してください。

<Question>
`key` を書く前と後で、結果はどう変わりましたか。
`key` には `loan.id` を使いました。もし、配列の中の位置（0, 1, 2…）を `key` にしたら、どうなるでしょうか。
</Question>

<Reveal>

`key` を書くと、メモは「リーダブルコード」の行に残ります。新しい行は、新しいDOMとして先頭に入ります。

完成版の `miniReact.ts` は、今回の子に対応する前回の子を、次のように探しています。

```ts
function findOldIndex(
  newChild: Child,
  index: number,
  oldChildren: Child[],
  oldIndexByKey: Map<unknown, number>,
): number | undefined {
  const key = keyOf(newChild);
  if (key !== undefined) return oldIndexByKey.get(key);
  return keyOf(oldChildren[index]) === undefined ? index : undefined;
}
```

`keyOf` は、仮想ノードから `key` を取り出す関数です。`oldIndexByKey` は、「この `key` の子は、前回は何番目だったか」を引ける表です。
`key` があれば、同じ `key` を持つ前回の子を探します。なければ、これまでどおり同じ位置の子を使います。相手が見つからなかった子（`undefined`）は、新しくDOMを作って、その位置に入れます。

配列の中の位置を `key` にすると、先頭に足したときに、どの備品も前回とは違う `key` を持つことになります（リーダブルコードは 0 から 1 に変わります）。今回の `key` が 0 の行は「新しい備品4」なので、前回の `key` が 0 だったリーダブルコードの行と対応づけられます。結果は「位置で対応づける」のと同じで、メモはずれたままです。
`key` は、「前回のどれと、今回のどれが同じものか」を伝える目印です。データの `id` のように、並び順が変わっても変わらない値を使います。

</Reveal>

## JSXの正体は？

`app.ts` の `view()` は、`h()` が何重にも入れ子になっていて、どこが表のどの部分なのかが読み取りにくくなっています。
そこで、同じ内容を、HTMLに似た書き方で書けるようにしたのが<Term>JSX</Term>です。下は、同じ貸出一覧をJSXで書いたものです。

<Sandbox spec={jsxSandbox} />

ブラウザは、JSXをそのまま実行できません。実行する前に、変換の道具（このページでは枠の中の仕組み、ふだんの開発ではViteなど）が、JSXをふつうの関数呼び出しに書き換えます。
先頭の2行のコメントは、その書き換え方の指示です。2行目の `@jsx h` が、「このファイルのJSXは、`h()` の呼び出しに書き換えてください」という意味です。たとえば、次の2つは同じ意味になります。

```tsx
<td>{loan.itemName}</td>
<input size={10} aria-label={`${loan.itemName}のメモ`} />
```

```ts
h('td', null, loan.itemName);
h('input', { size: 10, 'aria-label': `${loan.itemName}のメモ` });
```

タグの名前が1つ目の引数に、属性が2つ目の引数のオブジェクトに、タグの中身が3つ目以降の引数になります。

<Question>
JSXには、HTMLにはない決まりがあります。「JSXは `h()` の呼び出しに書き換えられる」ことから、次の2つの理由を説明してください。

- 関数が `return` できるJSXは、いちばん外側の要素が1つだけ。`return <td>A</td><td>B</td>` とは書けない。
- 波括弧 `{ }` の中に、`if` や `for` は書けない。
</Question>

<Reveal>

**いちばん外側の要素は1つ**：`return <td>A</td><td>B</td>` は、`return h('td', null, 'A') h('td', null, 'B')` と書いているのと同じです。関数が返せる値は1つだけなので、これは書けません。並べたいときは、1つの要素で包んで、その子にします。

**波括弧の中に `if` や `for` は書けない**：波括弧の中身は、`h()` の引数の位置にそのまま置かれます。引数に書けるのは、値になるもの（式）だけです。だから、出し分けには `条件 ? A : B`、くり返しには `map` を使います。

同じところから出てくる決まりが、あと2つあります。

**タグは必ず閉じる**：HTMLでは `<input>` を閉じなくても済みますが、それはブラウザが「`input` は子を持たない」と知っているからです。JSXは、タグごとの事情を知りません。どのタグも同じ決まりで、「ここまでがこの呼び出しの子です」と閉じて示します（`<input />`）。

**`class` ではなく `className` と書く**：JSXの属性は、`h()` の2つ目の引数になるオブジェクトのキーになります。そのため、属性の名前はJavaScriptでの名前に合わせます。`class` はJavaScriptでは別の意味を持つ言葉なので、DOMでの名前と同じ `className` を使います。`onClick` のように、単語をつないだ名前は2語目を大文字で始めます（キャメルケース）。`aria-label` のような `aria-` や `data-` で始まる属性だけは、HTMLと同じくハイフンで書きます。

ReactのJSXも、考え方は同じです。書き換え先が `h` ではなく、Reactが用意した関数になります（`createElement`、いまのReactでは同じ役目の `jsx`。引数の渡し方などの細かい点は違います）。
JSXはHTMLではありません。HTMLに似せて書ける、関数呼び出しの別の書き方です。

</Reveal>

## この仕組みは「速い」のか？

<Question>
ミニReactは、画面全体のオブジェクトを作り、前回のものと全部見比べてから、DOMを直します。
「1行目の状態の文字を書き換える」だけなら、0-2のA版のように直接DOMに書くのと比べて、速いでしょうか。遅いでしょうか。
</Question>

<Reveal>

速くはありません。直接書けば、DOMの操作を1回するだけです。ミニReactは、オブジェクトを全部作り、全部見比べたうえで、同じ操作を1回します。見比べるぶんは、追加の仕事です。

それでもこの仕組みを使うのは、速さのためではありません。「データから画面を書くだけ」という、直し忘れの起きない書き方を保ったまま、DOMの変更を必要なところだけに抑えられるからです。
0-1で見たとおり、重いのはDOMを変えたあとのレイアウトの再計算でした。DOMの変更が必要なところだけなら、見比べる手間を足しても、たいていは十分な速さで動きます。

</Reveal>

## ミニReactは、本物のReactの何にあたる？

<Question>
デモの右側（違うところだけ直す）では、1.5秒ごとの切り替えのたびに、2つのことが起きていました。
毎回まるごと作り直していたものは何で、ほんの少ししか変わらなかったものは何だったでしょうか。
</Question>

<Reveal label="答えと、Reactとの対応を見る">

毎回まるごと作り直していたのは、画面を表すオブジェクトです。ほんの少ししか変わらなかったのは、DOMです（文字が1か所だけ）。
Reactでは、この2つの段階に別々の名前が付いています。

| 今日作ったもの | Reactでの呼び名 |
|---|---|
| `h()` | `createElement`（いまのJSXの書き換え先は、同じ役目の `jsx`） |
| `h()` が返すオブジェクト（仮想ノード） | React要素 |
| `view()` を呼んで画面のオブジェクトを作り、前回と見比べること | <Term>レンダー</Term> |
| 見比べた結果を、DOMに書くこと | <Term>コミット</Term> |
| `key` | `key` |

レンダーしても、DOMが変わるとは限りません。見比べた結果、違いがなければ、DOMには何も書かれません。

ミニReactは、考え方をつかむための模型です。本物のReactとは、作りが違うところがあります。たとえば、ミニReactは見比べながらその場でDOMに書きますが、Reactは先に全部を見比べてから、まとめてDOMに書きます。
今日つかんでほしいのは、次の3つです。

- 画面を、状態から計算した「オブジェクトの木」として書く（UI = f(state)）。
- 前回の木と見比べて、違うところだけをDOMに反映する。
- 一覧では、どれとどれが同じものかを `key` で伝える。

</Reveal>

## よくある誤解

<Misconception wrong="仮想DOMがあるから、Reactは速い。">

見比べるぶんは追加の仕事で、必要なところを直接DOMに書くのと比べれば、速くはなりません。得ているのは速さではなく、状態から画面を書くだけで済む、という書きやすさです。仮想DOMは、そのための手段です。

</Misconception>

<Misconception wrong="再レンダリングとは、DOMを全部書き換えることだ。">

レンダーは、画面のオブジェクトを作り直すことです。DOMに書かれるのは、前回と違っていたところだけです。作り直した結果が前回と同じなら、DOMには何も書かれません。

</Misconception>

<Misconception wrong="key は、警告を消すために書くものだ。">

`key` は、前回のどれと今回のどれが同じものかを伝える目印です。警告を消すだけのために位置を `key` にしても、対応づけは変わりません。

</Misconception>

<Misconception wrong="JSXは、JavaScriptの中に書けるHTMLだ。">

JSXは、関数呼び出しの別の書き方です。いちばん外側が1つ、波括弧の中は式、タグは閉じる、`className` と書く、といった決まりは、どれもそこから出てきます。

</Misconception>
